# andrej-karpathy-rdb-ddl Plugin — Design Spec

**Date**: 2026-05-13
**Stage**: 2 of 4 (Backend — DDL Generation)
**Upstream**: Stage 1 `andrej-karpathy-rdb-skill` → `_blueprint.yaml`
**Downstream**: Stage 3 `/nexacro-fullstack-starter`

---

## 1. Goal

Build a Claude Code plugin that consumes the Stage 1 manifest (`_blueprint.yaml`) and emits a complete backend DDL artifact set:

- PostgreSQL DDL split into Flyway-compatible migrations (V001~V004)
- JPA Entity Java sources (Lombok-based, JDK 11+ compatible)
- Seed data SQL for preset entities
- `ddl-report.md` revalidation summary

The plugin is packaged separately from Stage 1 so each stage of the pipeline ships independently.

---

## 2. Inputs & Contract

### 2.1 Input file
`<wiki_path>/_blueprint.yaml` — the canonical output of Stage 1's `/karpathy-rdb compile`.

### 2.2 Required fields
```yaml
version: 1
project: <한국어 도메인명>
entities:                              # required
  - name: customer
    table: customer
    schema: crm                        # used as-is for PostgreSQL schema
    columns: [...]
    indexes: [...]
    constraints: [...]
relations: [...]                       # required
business_rules: [...]                  # required (enforced_by → CHECK)
validation:
  passed: true                         # false → abort
```

### 2.3 Abort conditions
| Condition | Action | Exit |
|---|---|---|
| `version != 1` | abort with message `"unsupported blueprint version: <v>"` | 1 |
| `validation.passed: false` | abort with message `"Stage 1 validation failed — run /karpathy-rdb compile again"` | 1 |
| Revalidation V001~V004 ERROR ≥ 1 | write `ddl-report.md`, abort | 1 |
| File IO failure | abort with stderr trace | 2 |
| Template rendering failure | abort with stderr trace | 3 |

## 3. Outputs

Written under `--out` (default `./db/`):

```
db/
├── migrations/
│   ├── V001__create_schema.sql       # CREATE SCHEMA IF NOT EXISTS …
│   ├── V002__create_tables.sql       # CREATE TABLE IF NOT EXISTS …
│   ├── V003__create_indexes.sql      # CREATE INDEX IF NOT EXISTS …
│   └── V004__create_constraints.sql  # ALTER TABLE … ADD CONSTRAINT FK / CHECK
├── seed/
│   └── 01_<entity>_sample.sql        # preset entities only, 3 rows each
├── src/main/java/<package>/
│   └── <Entity>.java                 # one file per entity
└── ddl-report.md
```

### 3.1 DDL format

All DDL is idempotent (`IF NOT EXISTS`). PostgreSQL 15+ syntax assumed. Schema names come directly from `entity.schema` — no romanization or transformation in this stage.

**Dialect support**: This stage ships **PostgreSQL 15+** and **HSQLDB 2.7+**. Generator functions accept a `dialect: str` parameter (`"postgres"` default, `"hsqldb"` opt-in). Templates live under `templates/<dialect>/`. Future dialects (e.g. MySQL) follow the same contract — see §9.1.

**HSQLDB specifics** (vs PostgreSQL):
- `BIGSERIAL` → `BIGINT GENERATED BY DEFAULT AS IDENTITY`
- `CREATE SCHEMA` is supported (schema strategy `"native"` — D2 preserved)
- `CREATE TABLE IF NOT EXISTS` supported (HSQLDB 2.x)
- Seed idempotency: HSQLDB uses `MERGE INTO <t> USING (VALUES …) AS s ON … WHEN NOT MATCHED THEN INSERT …`
- Regex operator: HSQLDB only supports `REGEXP_MATCHES(col, pattern)` as a function, no infix operator. CHECK constraints that use regex are emitted with this function; if a Stage 1 `enforced_by` cannot be translated, V005 downgrades to WARN and the constraint is skipped (per §4).

V002 table order is determined by topological sort over FK dependencies (relations). Self-referencing entities are allowed (FK constraint deferred to V004).

V004 emits:
- FK constraints: `ALTER TABLE <schema>.<table> ADD CONSTRAINT fk_<table>_<col> FOREIGN KEY (<col>) REFERENCES <ref_schema>.<ref_table>(<ref_col>) ON DELETE <action>;`
- CHECK constraints: derived from `business_rules[*].enforced_by` SQL expressions

### 3.2 JPA Entity format

```java
package com.example.<schema>;          // --package overridable

import jakarta.persistence.*;
import lombok.Data;
import lombok.NoArgsConstructor;
import lombok.AllArgsConstructor;

@Entity
@Table(name = "<table>", schema = "<schema>")
@Data
@NoArgsConstructor
@AllArgsConstructor
public class <Entity> {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    // ...
}
```

**Constraints**:
- Lombok `@Data + @NoArgsConstructor + @AllArgsConstructor` only
- No JDK17+ syntax: no `record`, no `sealed`, no pattern matching
- JDK 11+ compatible
- One file per entity, named `<PascalCase entity name>.java`
- Package: default `com.example.<schema>`, override via `--package <pkg>`

### 3.3 Seed format

Only entities whose Stage 1 origin is a preset (`고객관리`, `주문관리`, `재고관리`, `인사관리`, `재무관리`). Detection rule: an entity is "preset-sourced" if either (a) its blueprint entry carries a `preset: <name>` marker propagated from Stage 1, or (b) `(domain, name)` matches a known preset entry in the hardcoded preset catalog shipped with this plugin (`scripts/preset_catalog.py`). The catalog is the authoritative fallback when Stage 1 does not propagate the marker.

Each preset entity gets 3 sample rows via `INSERT … ON CONFLICT DO NOTHING`. Sample values are deterministic placeholders (`sample1@example.com`, `샘플고객1`, etc.).

Non-preset entities are skipped silently.

## 4. Revalidation (V001~V005)

Stage 2 re-runs all five validators at the DDL level after loading the blueprint.

| Code | Check | Failure condition | Severity |
|---|---|---|---|
| V001 | PK exists | Entity has no column with `pk: true` | ERROR |
| V002 | FK targets | `relation.to` missing, target entity has no PK, FK column type mismatch | ERROR |
| V003 | Naming | snake_case violation, PostgreSQL reserved word, identifier > 63 chars | ERROR |
| V004 | Schema consistency | `entity.schema` missing, cross-schema FK not declared in relation | ERROR |
| V005 | Constraint translatable | `business_rules[*].enforced_by` SQL expression fails parse-check | WARN |

ERROR (V001~V004) aborts compilation. WARN (V005) skips that constraint and records it in `ddl-report.md`.

## 5. Architecture (Approach A — Python CLI single compiler)

Stage 2 mirrors Stage 1's structure: a Python CLI with Jinja2 templates and pytest TDD coverage.

### 5.1 Data flow

```
_blueprint.yaml
    ↓
[1] Loader (loader.py)         — PyYAML parse + version/validation check
    ↓
[2] Revalidator (revalidator.py) — V001~V005 checks
    ↓
[3] Toposort (toposort.py)     — FK-dependency entity ordering
    ↓
[4] DDL Generator (ddl_gen.py) — Jinja2 → 4 SQL files
[5] JPA Generator (jpa_gen.py) — Jinja2 → .java files
[6] Seed Generator (seed_gen.py) — Jinja2 → SQL files (preset only)
    ↓
[7] Report writer              — ddl-report.md
```

Steps 4–6 run sequentially after [3]. Failure in any step aborts with the appropriate exit code.

### 5.2 Tech stack
- Python 3.11+
- PyYAML (parsing)
- Jinja2 (templating)
- pytest (testing)
- argparse (CLI)

Same dependencies as Stage 1.

### File responsibilities

|---|---|---|
| `ddl_compile.py` | CLI entrypoint, orchestrates pipeline, exit codes | `main(argv) -> int` |

| `revalidator.py` | Run V001~V005, return ERROR/WARN list | `revalidate(blueprint) -> List[Diagnostic]` |
| `toposort.py` | Sort entities by FK dependency, detect cycles | `topo_sort(entities, relations) -> List[entity]` |
| `ddl_gen.py` | Render 4 migration files via Jinja2 | `generate_ddl(entities, relations, business_rules, out_dir, dialect="postgres")` |
| `jpa_gen.py` | Render JPA entity .java files | `generate_jpa(entities, package, out_dir)` |
| `seed_gen.py` | Render seed SQL for preset entities | `generate_seed(entities, out_dir, dialect="postgres")` |
| `dialect.py` | Per-dialect type/syntax mapping table; selects template directory | `get_dialect(name) -> Dialect` |
| `preset_catalog.py` | Hardcoded `{(domain, name) → preset_id}` catalog for fallback preset detection | `is_preset(entity) -> bool` |

## 7. Slash Command

**Location**: `.claude/commands/rdb-ddl-compile.md`

**Usage**:
```
/rdb-ddl-compile <wiki_path> [--out <output_dir>] [--package <java_pkg>] [--dialect <postgres|hsqldb>]
```

**Defaults**:
- `<wiki_path>`: required, must contain `_blueprint.yaml`
- `--out`: `./db/`
- `--package`: `com.example.<schema>`
- `--dialect`: `postgres` (alternative: `hsqldb`)

**Command body**:
1. Verify `<wiki_path>/_blueprint.yaml` exists; if not, abort with guidance
2. Invoke `python scripts/ddl_compile.py <wiki>/_blueprint.yaml --out <out> --package <pkg>`
3. On exit 0: print artifact paths + statistics
4. On nonzero exit: surface `ddl-report.md` location and abort message

## 8. Testing Strategy (TDD)

Every module is written test-first. Tests are organized by module, plus one integration test against a frozen golden blueprint.

| Test file | Cases |
|---|---|
| `test_loader.py` | Parse valid yaml; reject missing `version`; reject `validation.passed: false` |
| `test_revalidator.py` | RED + GREEN for each of V001~V005 (10 cases total) |
| `test_toposort.py` | Linear chain, diamond, cycle (raises), self-reference |
| `test_ddl_gen.py` | V001~V004 each contain expected SQL fragments; `IF NOT EXISTS` present; toposort order respected (PostgreSQL) |
| `test_ddl_gen_hsqldb.py` | Same coverage but for HSQLDB: `BIGINT GENERATED BY DEFAULT AS IDENTITY`, `MERGE INTO` seed, `REGEXP_MATCHES` in CHECK |
| `test_jpa_gen.py` | Lombok annotations present; @Table(schema=…) set; regex check ensures no `record`/`sealed`/`switch (…) ->` syntax; one file per entity |
| `test_seed_gen.py` | Preset entities produce SQL; non-preset entities skipped; exactly 3 rows per file; `ON CONFLICT DO NOTHING` present |
| `test_golden_path.py` | `golden_blueprint.yaml` → full output tree; revalidation passes; all artifacts non-empty |

**Golden fixture**: derived from Stage 1's `golden_wiki` by running `/karpathy-rdb compile`, then committed as `tests/fixtures/golden_blueprint.yaml`.

## 9. Out of Scope (This Stage)

- Liquibase migration format (Flyway only)
- Repository / Service / Controller Java code (Stage 3 territory)
- Spring Boot project scaffolding (`pom.xml`, `application.yml`) (Stage 3)
- Stage 1 wiki editing (this stage is read-only on the wiki)
- MySQL and other dialect implementations — see §9.1 (PostgreSQL + HSQLDB are in-scope this stage)
- Data migration scripts (only schema DDL + seed)
- Reverse-engineering existing databases (forward generation only)

### 9.1 Dialect Extension Contract

Code is structured so future dialects can be added without touching the pipeline. To add e.g. MySQL:

1. Add `templates/mysql/{schema,tables,indexes,constraints,seed}.sql.j2`
2. Register a `Dialect` entry in `dialect.py` with:
   - `type_map: {bigserial: "BIGINT AUTO_INCREMENT", varchar: "VARCHAR", timestamp: "DATETIME", ...}`
   - `schema_strategy: "prefix" | "native"` — MySQL is `"prefix"` (no CREATE SCHEMA; tables become `<schema>_<table>`), PostgreSQL/HSQLDB are `"native"`
   - `idempotent_insert: "ON CONFLICT DO NOTHING" | "INSERT IGNORE" | "MERGE"`
   - `regex_op: str | None` — for CHECK constraint translation (PostgreSQL `~`, MySQL `REGEXP`, HSQLDB `None` → V005 WARN)
3. Add `--dialect mysql` choice to CLI argparse
4. Add a corresponding `test_<dialect>_gen.py` golden-output test

JPA generator and revalidator are dialect-agnostic and do not change.

**Schema strategy clash with D2**: under `"prefix"` strategy, the domain-isolation promise of D2 weakens (everything in one DB, table names get prefixed). This is acceptable for MySQL because MySQL has no schema concept; future MySQL adopters trade D2's isolation for compatibility. PostgreSQL/HSQLDB preserve D2 fully.

## 10. Decision Log

| ID | Decision | Rationale |
|---|---|---|
| D1 | Single `compile` command | Mirrors Stage 1 `/karpathy-rdb compile`. One-shot pipeline. |
| D2 | Domain-separated PostgreSQL schemas | Aligns with Korean domain model. Isolation between domains. |
| D3 | Lombok `@Data`-style JPA, no JDK17+ syntax | Per user constraint. JDK 11+ compatible. |
| D4 | `entity.schema` used as-is | Stage 1 already owns the mapping decision. |
| D5 | PostgreSQL 15+ | Modern syntax. Common deployment target. |
| D6 | V001~V004 four-file migration split | Matches Stage 2 spec doc. Clean concern separation. |
| D7 | `IF NOT EXISTS` idempotent | Safe re-runs. Compatible with Flyway baseline. |
| D8 | Seed for preset entities only, 3 rows each | Bounded scope. Predictable output. |
| D9 | Revalidate V001~V005 at DDL level | Final gate before downstream stages. |
| D10 | Approach A: Python CLI + Jinja2 + pytest | Consistency with Stage 1. Lowest learning cost. |
| D11 | Implement PostgreSQL + HSQLDB; structure for further dialect extension | Two dialects in-scope (Postgres prod / HSQLDB embedded tests). MySQL etc. follow §9.1 contract. |
