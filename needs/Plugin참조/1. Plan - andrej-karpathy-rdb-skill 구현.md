

안드레이 카파시(Andrej Karpathy)가 제안한 **LLM Wiki** 패턴은 파편화된 정보를 LLM이 직접 구조화된 마크다운(Markdown) 문서로 관리하게 하여 지식을 복리로 쌓는 방식입니다. 이를 관계형 데이터베이스(RDBMS) 환경의 **비즈니스-도메인-엔티티** 구조에 적용할 경우, 다음과 같은 관리 방안을 도출할 수 있습니다. [](https://www.mindstudio.ai/blog/karpathy-llm-wiki-pattern-cut-claude-token-usage-95-percent)

1. 3계층 아키텍처 적용 (구조 설계)

카파시의 방식을 데이터베이스 설계와 문서화에 이식하면 다음과 같이 역할을 나눌 수 있습니다. [](https://www.youtube.com/watch?v=iXd0t60YmMw&t=160)


- **Raw Sources (원본 데이터)**: DB 스키마(DDL), 실제 비즈니스 요구사항 명세서, 회의록, 기존 레거시 코드 등 수정되지 않는 '진실의 근원'입니다.
- **The Wiki (LLM 관리 계층)**: LLM이 원본 데이터를 읽고 생성한 **비즈니스 로직 설명, 도메인 지식, 엔티티 정의서**입니다. 마크다운 파일로 관리되며, 상호 연결([[Wiki Link]])을 통해 데이터 간의 관계를 시각화합니다.
- **Schema (규칙 정의)**: `CLAUDE.md`와 같은 설정 파일에 "엔티티 변경 시 관련 도메인 페이지를 갱신하라"는 규칙을 정의하여 LLM이 일관성 있게 관리하도록 합니다. [](https://www.youtube.com/watch?v=iXd0t60YmMw&t=160)

2. 비즈니스-도메인-엔티티 관리 전략

RDBMS의 핵심 요소들을 카파시 위키 패턴으로 관리하는 구체적인 프로세스는 다음과 같습니다.

|관리 대상|카파시 위키 적용 방안|기대 효과|
|---|---|---|
|**비즈니스 로직**|요구사항 변화에 따라 LLM이 `index.md`나 `log.md`를 갱신하며 비즈니스 맥락의 변화를 기록.|의사결정 이력(ADR)의 자동화 및 맥락 유지|
|**도메인(Domain)**|특정 도메인(예: 결제, 주문)별로 개념 페이지를 생성하고 소속 엔티티들을 링크로 연결.|도메인 전문가와 개발자 간의 지식 격차 해소|
|**엔티티(Entity)**|각 테이블이나 객체를 개별 페이지로 관리. 속성 설명뿐 아니라 실제 DB 스키마와의 정합성을 LLM이 체크.|최신화된 데이터 사전(Data Dictionary) 유지|

3. 주요 운영 방안: "컴파일러로서의 LLM"

이 방식의 핵심은 사람이 문서를 쓰는 것이 아니라, **LLM이 '지식 컴파일러' 역할**을 수행하게 하는 것입니다. 

- **상충 관리 (Contradiction Detection)**: 새로운 엔티티 추가 시 기존 도메인 로직과 충돌하면 LLM이 이를 즉시 감지하여 수정 제안을 합니다.
- **복리식 지식 축적 (Compounding Knowledge)**: 질문과 답변 과정을 거치며 얻은 새로운 인사이트를 다시 위키에 반영하여, 시간이 지날수록 검색이 아닌 '추론'이 가능한 지식 베이스가 됩니다.
- **파일 기반 인터페이스**: 데이터베이스 내부가 아닌 Obsidian과 같은 툴로 열 수 있는 로컬 마크다운 파일로 관리하여 개발 에이전트(Claude Code 등)가 즉시 읽고 쓸 수 있게 합니다. [](https://blog.pebblous.ai/report/karpathy-llm-wiki/en/)


이러한 방식은 기존의 정적인 DB 설계서가 시간이 흐름에 따라 낡아버리는 고질적인 문제를 해결하고, AI가 비즈니스 맥락을 완벽히 이해한 상태에서 개발을 보조할 수 있는 환경을 제공합니다.
