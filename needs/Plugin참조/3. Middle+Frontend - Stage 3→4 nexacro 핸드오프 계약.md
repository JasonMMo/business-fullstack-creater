# 3~4단계 : Stage 3 → Stage 4 nexacro 핸드오프 계약

> 본 문서는 `andrej-karpathy-rdb-mybatis` (Stage 3, v0.1.3) 가 생성한 MyBatis 백엔드 산출물을 외부 plugin `nexacro-fullstack-starter` (Stage 4, v0.6.0) 가 생성한 scaffold 위에 어떻게 얹는지(overlay) 정의한다.

## 1. 실행 순서 (반드시 이 순서)

```
[1] Stage 4 scaffold (빈 디렉터리에 부어넣기)
       │
       ▼
   ./<PROJECT_NAME>/{nxui/, src/, pom.xml, README.md}
       │
[2] Stage 3 overlay (위 디렉터리에 덮어쓰기)
       │
       ▼
   ./<PROJECT_NAME>/src/{main/java/com/nexacro/uiadapter, main/resources}
```

이유:
- Stage 4 는 `TARGET_DIR` 이 존재하면 **중단** (덮어쓰기 안 함) — 따라서 빈 디렉터리에 먼저 부어야 한다.
- Stage 3 는 `pom.xml`, `application.yml`, `Application.java`, `config/` 를 **건드리지 않는다** — Stage 4 가 제공하는 인프라 코드 위에 도메인 코드만 얹는 모델.

## 2. 패키지/경로 정합성

| 항목 | Stage 4 scaffold | Stage 3 overlay | 일치 |
| :-- | :-- | :-- | :--: |
| 루트 패키지 | `com.nexacro.uiadapter` | `com.nexacro.uiadapter` | ✅ |
| 컨트롤러 | `controller/` | `controller/<Entity>Controller.java` | ✅ |
| 서비스 인터페이스 | `service/` | `service/<Entity>Service.java` | ✅ |
| 서비스 구현 | `service/impl/` | `service/impl/<Entity>ServiceImpl.java` | ✅ |
| Mapper 인터페이스 | `mapper/` | `mapper/<Entity>Mapper.java` | ✅ |
| 도메인 | `domain/` | `domain/<Entity>.java` | ✅ |
| Mapper XML | (없음 / 샘플) | `resources/mybatis/mapper/<Entity>Mapper.xml` | ✅ overlay |
| 스키마 | `resources/schema.sql` (샘플) | `resources/schema.sql` (생성본) | ⚠ 덮어쓰기 |
| 시드 | `resources/data.sql` (옵션) | `resources/data.sql` (옵션) | ⚠ 덮어쓰기 |

`Stage 3` 출력 기준 (`references/output-layout.md`):

```
src/main/java/com/nexacro/uiadapter/
├── controller/<Entity>Controller.java
├── service/<Entity>Service.java
├── service/impl/<Entity>ServiceImpl.java
├── mapper/<Entity>Mapper.java
└── domain/<Entity>.java
src/main/resources/
├── schema.sql
├── data.sql                (seed 가 있으면)
└── mybatis/mapper/<Entity>Mapper.xml
mybatis-report.md            (overlay 시 .gitignore 또는 docs/ 로)
```

## 3. 충돌 처리 정책

| 파일 종류 | 정책 |
| :-- | :-- |
| `BoardController.java` 등 scaffold 샘플 클래스 | **유지** — Stage 3 가 같은 이름의 entity 를 만들지 않는 한 공존. 충돌 시 Stage 3 가 wins (덮어쓰기). |
| `schema.sql`, `data.sql` | scaffold 본을 **백업**(`*.scaffold.sql`) 후 Stage 3 본으로 교체. |
| `mybatis-config.xml`, `application.yml` | Stage 4 본 그대로 사용. Stage 3 가 건드리지 않음. |
| `pom.xml`, `Application.java`, `config/*.java` | Stage 4 본 그대로 사용. Stage 3 가 건드리지 않음. |
| `mybatis-report.md` | overlay 후 `<PROJECT_ROOT>/docs/` 로 이동 권장 (또는 `.gitignore`). |

## 4. 사전 조건 (Stage 4 가 만족시켜 주는 것)

Stage 3 가 만든 코드가 빌드되려면 scaffold 측이 아래를 보장해야 한다. v0.6.0 기준 모두 충족됨:

- `Application.java` + `@SpringBootApplication` (JDK17 / Boot 3 / jakarta lane 의 경우)
- `application.yml` 의 `mybatis.mapper-locations: classpath:mybatis/mapper/*.xml` 또는 `classpath*:mybatis/mapper/**/*.xml`
- `mybatis-spring-boot-starter` 의존성 (`pom.xml`)
- uiadapter jakarta 의존성: `com.nexacro.uiadapter.jakarta.core.*` 사용 가능
- HSQLDB 임베디드 DB 의존성 + `schema.sql` 자동 로드 설정

## 5. JDK / lane 매핑

| Stage 3 가 emit 하는 import | 호환 Stage 4 runner |
| :-- | :-- |
| `com.nexacro.uiadapter.jakarta.core.*` | `boot-jdk17-jakarta` (Spring Boot 3 + JDK17) |
| `com.nexacro.uiadapter.spring.core.*` (legacy) | `boot-jdk8-javax` (Spring Boot 2 + JDK8) ※ Stage 3 현재 미발행 |

> Stage 3 는 현재 **jakarta lane만** 생성한다. javax/JDK8 lane 지원이 필요하면 Stage 3 의 import alias 를 lane 파라미터로 분기해야 한다. → 후속 작업 (Task TBD)

## 6. 핸드오프 실행 스크립트 (참조 구현)

```bash
# 0) 입력
PROJECT_NAME="customer-mgmt"
WIKI_DIR="./.smoke/wiki"          # Stage 1 입력
OUT_BACKEND="./.smoke/backend"    # Stage 3 출력

# 1) Stage 4 — scaffold
/nexacro-fullstack-starter --jdk 17 --framework spring-boot --name "${PROJECT_NAME}"
# → ./${PROJECT_NAME}/ 생성

# 2) Stage 1+2+3 — 코드 생성 (이미 완료되어 있다 가정)
# 또는: python compile.py --blueprint .../{_blueprint.yaml} --ddl-dir .../migrations --out ${OUT_BACKEND}

# 3) Overlay
cp -r ${OUT_BACKEND}/src/main/java/com/nexacro/uiadapter/. \
      ./${PROJECT_NAME}/src/main/java/com/nexacro/uiadapter/
cp -r ${OUT_BACKEND}/src/main/resources/mybatis/. \
      ./${PROJECT_NAME}/src/main/resources/mybatis/

# schema.sql / data.sql 은 scaffold 본 백업 후 교체
mv ./${PROJECT_NAME}/src/main/resources/schema.sql{,.scaffold} 2>/dev/null || true
mv ./${PROJECT_NAME}/src/main/resources/data.sql{,.scaffold}   2>/dev/null || true
cp ${OUT_BACKEND}/src/main/resources/schema.sql ./${PROJECT_NAME}/src/main/resources/
[ -f ${OUT_BACKEND}/src/main/resources/data.sql ] && \
  cp ${OUT_BACKEND}/src/main/resources/data.sql ./${PROJECT_NAME}/src/main/resources/

# 4) mybatis-report.md → docs/
mkdir -p ./${PROJECT_NAME}/docs
mv ${OUT_BACKEND}/mybatis-report.md ./${PROJECT_NAME}/docs/

# 5) 검증
cd ./${PROJECT_NAME}
mvn -q -DskipTests compile     # R006 (javac) 와 동등
```

## 7. 검증 체크리스트 (overlay 후)

- [ ] `mvn -q -DskipTests compile` 성공 — javac 가 Stage 3 + Stage 4 클래스 모두 합쳐 컴파일 통과
- [ ] `src/main/java/com/nexacro/uiadapter/Application.java` 존재 (Stage 4 보존)
- [ ] `src/main/java/com/nexacro/uiadapter/controller/` 에 Stage 3 가 만든 `<Entity>Controller.java` 존재
- [ ] `src/main/resources/mybatis/mapper/<Entity>Mapper.xml` 의 `namespace` 가 `com.nexacro.uiadapter.mapper.<Entity>Mapper` 와 동일
- [ ] `schema.sql` 의 `NOT NULL` 제약이 Stage 1 blueprint 의 `nullable: false` 컬럼과 1:1 매핑 (`nullable` 키 정렬 회귀 점검)
- [ ] `mvn spring-boot:run` 후 `http://localhost:8080/uiadapter/` 가 응답
- [ ] `POST /uiadapter/<entity>/select_datalist_map` 호출 시 NexacroResult 직렬화 성공 (license 설치된 경우)
